# NEXORA Distribution OS — تجهيز ما قبل النشر على Blitz Cloud

**الحالة:** مسودة تجهيز فقط — لا يوجد نشر أو اعتماد إنتاجي.

**القاعدة:** هذا الملف لا يجيز رفع الكود أو إنشاء موارد مدفوعة أو نقل بيانات حقيقية. يلزم إذن صريح منفصل قبل أي خطوة من هذه الخطوات.

## 1. الوضع الحالي

- المشروع يحتوي على واجهة Next.js مستقلة داخل `frontend/` وواجهة API باستخدام Laravel داخل `backend/`.
- `Dockerfile` متعدد المراحل موجود، و`docker-compose.yml` الحالي مخصص لتشغيل محلي يشمل MySQL 8.4 وAPI وواجهة Next.js.
- إعداد Next.js يستخدم `output: standalone` ويمرّر طلبات `/api/*` إلى `API_INTERNAL_URL`، مع قيمة محلية افتراضية؛ يجب تعيين عنوان داخلي صحيح في بيئة النشر.
- توجد تغييرات كثيرة غير معتمدة في شجرة العمل. يجب الحفاظ عليها وعدم استخدام `git reset`, `git clean`, أو تبديل/استبدال الملفات بغرض تجهيز النشر.
- قاعدة SQLite المحلية/المعاينة ليست قاعدة إنتاج، ولا يجوز نسخها تلقائيًا إلى خدمة الاستضافة أو اعتبارها مصدر الأرصدة الحقيقية.
- سجل المشروع يصفه بأنه Local Alpha، ويشترط مراجعات واختبارات إضافية قبل اعتماد عمليات المخزون والمال الحقيقية.

## 2. شكل النشر المستهدف (مبدئي)

1. واجهة Next.js عبر HTTPS على رابط الاستضافة المؤقت.
2. Laravel API كخدمة داخلية أو خلف مسار `/api` على نفس النطاق، من دون كشف منفذ قاعدة البيانات للعامة.
3. قاعدة MySQL متوافقة مع migrations الحالية، في خدمة منفصلة ومحمية. لا نفترض توافق MariaDB أو أي إصدار آخر قبل اجتياز الاختبارات.
4. تخزين دائم لملفات Laravel اللازمة، مع سياسة واضحة لملفات الفواتير المرفوعة والمرفقات. لا تعتمد على نظام ملفات مؤقت للحفظ طويل الأجل.
5. نسخ احتياطية مستقلة عن الخدمة واختبار استرجاع موثق.

## 3. متغيرات البيئة التي يجب ضبطها في لوحة الاستضافة

### Laravel API

- `APP_ENV=production`
- `APP_DEBUG=false`
- `APP_URL` = عنوان HTTPS الفعلي بعد الحصول على رابط الاستضافة
- `APP_KEY` = مفتاح سري خاص بهذه البيئة؛ لا يُنشأ أو يُشارك في ملف Docker ولا يُعاد توليده بعد وجود بيانات جلسات/تشفير حقيقية
- `DB_CONNECTION=mysql`
- `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` = بيانات خدمة قاعدة البيانات المستهدفة، بصلاحية أقل ما يمكن
- `SESSION_SECURE_COOKIE=true` عند تأكيد HTTPS ودعم إعداد الجلسات الحالي
- `LOG_LEVEL=warning` أو قيمة مناسبة بعد التأكد من عدم فقدان سجلات التشخيص اللازمة
- مراجعة `CACHE_STORE`, `QUEUE_CONNECTION`, `SESSION_DRIVER` والتأكد من وجود الجداول/العمال المطلوبة قبل اختيار `database`
- `FILESYSTEM_DISK` يجب أن يشير إلى تخزين دائم إذا كان النظام سيحتفظ بمرفقات فواتير أو مستندات

### Next.js frontend

- `NODE_ENV=production`
- `API_INTERNAL_URL` = عنوان Laravel الداخلي الذي يمكن للواجهة الوصول إليه من داخل بيئة الاستضافة
- `NEXT_PUBLIC_API_URL=/api/v1` إذا كان المرور عبر same-origin rewrite هو التصميم النهائي
- قيمة `NEXT_PUBLIC_*` تدخل في ملفات المتصفح وقت البناء؛ أي تغيير لها يستلزم إعادة بناء الواجهة.

**ممنوع:** إضافة أي `.env` حقيقي أو كلمات مرور أو مفاتيح إلى Git أو Docker image أو سجلات CI. تستخدم أسرار لوحة الاستضافة المخصصة.

## 4. بوابات ما قبل النشر

- [ ] توثيق مصدر البيانات الحقيقية ومالكها، وفصلها عن بيانات Alpha التجريبية.
- [ ] جرد شجرة Git والتغييرات غير المرفوعة وتحديد الملفات التي يجب أن تدخل في إصدار مرشح، دون حذف أو staging أو commit أو push تلقائي.
- [ ] مراجعة `.dockerignore` للتأكد من استبعاد `.env`، وقواعد SQLite، وملفات النسخ الاحتياطية، وملفات بيانات الدخول المحلية، ومخرجات الاختبارات.
- [ ] بناء صور Docker محليًا واختبار health checks، من دون نشرها.
- [ ] تشغيل اختبارات migrations والقيود والاختبارات الخلفية على إصدار قاعدة البيانات المستهدف، باستخدام قاعدة اختبار فارغة منفصلة فقط.
- [ ] اختبار تسجيل الدخول، عزل المؤسسات/المستأجرين، صلاحيات الموظف والمندوب، انتهاء الجلسة، ومشاركة الفاتورة.
- [ ] اختبار شراء ← تحميل سيارة ← بيع بسعر العميل ← تحصيل ← تسوية رحلة، والتحقق من رصيد المخزون والقيود المالية.
- [ ] مراجعة سياسات الضرائب والخصومات والمرتجعات وفروق الجرد والائتمان وترقيم المستندات قبل اعتماد استخدامها الفعلي.
- [ ] إعداد نسخة احتياطية قبل أي ترحيل، والتحقق من سلامتها، وتنفيذ تجربة استرجاع في بيئة منفصلة.
- [ ] اختبار نقل بيانات تجريبي على قاعدة فارغة، مع تقرير مطابقة للأعداد والأرصدة قبل/بعد النقل.
- [ ] إعداد حسابات مستقلة وصلاحيات أقل ما يمكن، ومراجعة سجلات التدقيق ومعدل الطلبات والحماية من تكرار إرسال المعاملة.
- [ ] مراجعة شروط خطة الاستضافة وتكلفتها وقيود الخدمات قبل إنشاء أي مورد؛ لا تُنشأ خدمات مدفوعة دون موافقة المالك.

## 5. سياسة الترحيل وحماية البيانات

1. لا ترحيل مباشر من SQLite المحلية إلى الإنتاج.
2. لا تستورد أرصدة افتتاحية من ملف غير معتمد أو من دون محضر مطابقة.
3. أنشئ نسخة احتياطية مشفرة خارج خدمة قاعدة البيانات قبل الترحيل، وحدد مدة الاحتفاظ والوصول إليها.
4. جرّب الاستيراد على قاعدة staging منفصلة، وقارن عدد العملاء والموردين والأصناف والمستندات والأرصدة.
5. عند أي اختلاف، أوقف الترحيل واحتفظ بالمصدر دون تعديل.
6. بعد قبول الترحيل فقط، يمكن التخطيط لنافذة تشغيل بموافقة صريحة؛ لا تستبدل سير العمل القديم قبل مطابقة الأرصدة.

## 6. خطة إصدار آمنة عند اكتمال التطوير

1. تجميد التغييرات للمرشح النهائي بموافقة المالك، ثم إنشاء commit/branch إصدار بعد مراجعة قائمة الملفات.
2. نجاح CI للواجهة والـ API، واختبارات قاعدة البيانات على المحرك والإصدار المستهدفين.
3. مراجعة إعدادات الأسرار والاتصالات والتخزين الدائم والنسخ الاحتياطي.
4. نشر نسخة اختبارية بلا بيانات حقيقية، واختبارها من هاتف/حاسوب خارج شبكة المطور.
5. طلب موافقة منفصلة على إنشاء/تفعيل موارد الاستضافة أو أي تكلفة.
6. طلب موافقة منفصلة على نقل البيانات الحقيقية وفتح الرابط للموظفين والمندوبين.
7. تفعيل مراقبة وصحة الخدمات، وخطة رجوع إلى إصدار التطبيق السابق. الرجوع لا يعني التراجع عن migrations مدمرة؛ migrations الإنتاجية يجب أن تكون متوافقة للخلف أو لها خطة ترحيل معتمدة.

## 7. ما لم يتم عمله

- لم يُنشر أي شيء إلى Blitz Cloud.
- لم يُنشأ رابط عام ولم تُنشأ خدمة أو قاعدة بيانات سحابية.
- لم يتم شراء دومين أو تفعيل اشتراك مدفوع.
- لم يتم نقل أو تعديل بيانات إنتاجية.
- لم يتم تعديل `Dockerfile` أو `docker-compose.yml` في هذه المرحلة؛ يلزم أولًا تأكيد تفاصيل runtime والخدمات المتاحة في خطة Blitz المختارة.
